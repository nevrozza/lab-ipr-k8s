# Распределение нагрузок (NodeAffinity) и хранилище файлов

В данном разделе описана логика распределения компонентов по физическим узлам кластера и организация хранения бинарных данных.

## 1. Конфигурация NodeAffinity

С целью оптимального распределения ресурсов кластера применены правила привязки подов к меткам нод (`workload=system` и `workload=app`):

### Инфраструктурный слой (Postgres, MinIO, Миграции)
Для баз данных и хранилищ настроено soft условие (`preferredDuringSchedulingIgnoredDuringExecution`) к запуску на нодах с меткой `workload=system`. Это позволяет инфраструктуре работать на выделенных узлах в продакшене, но запускаться на единственной ноде при локальном тестировании.

### Прикладной слой (Frontend, BFF, User Service)
Для бизнес-логики настроено soft условие к размещению на нодах с меткой `workload=app`.

### Message Service
Согласно ТЗ, для `message-service` настроена строгая комбинация условий:
1. **Hard условие:** Под обязан запускаться исключительно на нодах с меткой `workload=app`. При отсутствии таких нод планировщик переведет под в статус `Pending`.
2. **Soft условие:** Под стремится попасть на ноды с быстрой дисковой подсистемой (`disk=fast`), если такие доступны в кластере.

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: workload
              operator: In
              values: ["app"]
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        preference:
          matchExpressions:
            - key: disk
              operator: In
              values: ["fast"]
```

## 2. Организация хранения файлов (S3 CSI)

Микросервис сообщений поддерживает загрузку картинок и файлов. 

### Конфигурация в Prod-окружении
Для хранения файлов используется S3-совместимое хранилище (MinIO), монтируемое внутрь контейнера через CSI-драйвер (`ru.yandex.s3.csi` или аналогичный). 
* Манифест `s3-csi.yaml` описывает `PersistentVolume` и `PersistentVolumeClaim`, связывая бакет `uploads` с директорией `/app/uploads` в контейнере `message-service`.

### Локальная эмуляция в Dev-окружении
* **Проблема:** При локальном тестировании (на macOS/Windows через Docker Desktop/Minikube) отсутствует развернутый S3 CSI драйвер. Использование стандартного `hostPath` приводило к ошибке `500` на запросе `POST /api/v1/files`, так как у локального пользователя внутри контейнера не хватало прав операционной системы на запись в проброшенную папку хоста.
* **Решение:** В оверлее `dev` деплоймент `message-service` патчится – том `uploads` переводится на тип **`emptyDir`**. Оно не зависит от прав хостовой ОС, всегда доступно на запись и позволяет полноценно тестировать отправку изображений локально. При этом продуктовые манифесты остаются чистыми и используют полноценный CSI.
